# 性能与容量实测

> 全部数据来自真机实测（V100-SXM2-16GB，宿主 15.5 GiB）。
> 现役配置：`-c 131072 -n 16384 --kvmem-budget 24576 --kvmem-gen-reserve 16384 --kv-dtype q5_0`

---

## 1. 速度

### 1.1 随上下文长度的变化

| 场景 | prefill (t/s) | decode (t/s) |
|---|---:|---:|
| 首遍 2K tokens | 574 | — |
| 4.8K tokens | 508 | 36–38 |
| 6.7K tokens | 553–544 | 35.7–37.9 |
| 14.3K tokens | 456–514 | 39.2–41.2 |
| **66.7K（受控压测）** | **424.6** | — |
| **69.9K（真实 Codex 请求）** | 405→411 瞬时 / **337.9 平均** | **40.8–44.4** |
| 官方参照（RTX 5060 Ti，满 256K） | 436.7 首遍 / 243.2 有效 | 29.96 |

**读数**：

- **prefill**：从 2K 的 574 t/s 衰减到 66.7K 的 424.6 t/s —— 约 **−26%**。
  这是 `--kvmem-budget` 的代价：上下文越长，每步检索要搬运的块越多。
- **decode**：**36–44 t/s**，且**不随上下文长度明显衰减**（4.8K 时 36–38，69.9K 时 40.8–44.4）。
  块稀疏调度把 decode 的注意力成本压住了。
- **V100 的 decode（40–44）明显优于官方参照的 29.96**，prefill 同档。

### 1.2 ⚠️ 一个会误导人的现象：prefill 末尾"停摆"

**当上下文超过 `budget + gen_reserve` 之后，prefill 末尾有数十秒的"停摆"**：

```
68K 请求：进度行在 170.9s 走完
          但 prompt eval time 报 206.8s
          → 36s 的差额不计入任何 t/s 进度行
```

**这 36 秒是真实存在的**，但不会出现在任何进度行里。
如果你用进度行的 t/s 去算端到端时间，会**严重低估**。

> **解释**：这一段是超出 GPU 窗口的 KV 回捞/重映射阶段，服务不更新进度行。

## 2. 宿主内存模型验证

### 2.1 同一 prompt 的 A/B 复测（66,686 token）

这是最干净的对照——**同一个 prompt、同一台机器、同一份模型**，只有 `-c` 不同：

| 指标 | `-c 98304`（旧基线） | `-c 131072`（干净基线） |
|---|---:|---:|
| 起始 anon | 6387 MiB | **246 MiB** |
| 峰值 anon | 8153 MiB | **2132 MiB** |
| Δanon | 1766 MiB | 1886 MiB |
| **斜率** | **27.1 KiB/tok** | **29.0 KiB/tok** |
| prefill | 424.6 t/s | **449.4 t/s** |
| wall | 161 s | 151 s |
| file（page cache） | 6423 → 5078（**被驱逐**） | 10228（**不变**） |
| swap | 2312 MiB | 2130 MiB（未动） |
| GPU 显存 | — | 13132 → 13866 MiB |

**三条结论**：

1. **斜率两次一致**（27.1 / 29.0 KiB/tok）→ **每 token 成本模型成立**。
   理论值 q5_0 是 22 KiB/tok，实测略高（额外开销），同档。
2. **`-c` 越大 ≠ 越贵**：`-c 131072` 的起始 anon 反而只有 246 MiB。
3. **内存压力会拖慢速度**：旧基线 prefill 慢 5.8%，
   因为 page cache 被驱逐、swap 在抖动。**内存健康 = 性能健康。**

### 2.2 池子不随请求缩小

| 观测 | 值 |
|---|---|
| 20:13 发一个 **852 token** 的小请求 | 容器 anon 仍是 **6482 MiB** |

**KV 池是"高水位"语义**：涨上去就不会因为请求变小而降下来。
→ 这正是「**重启容器清池**」成为最直接杠杆的原因。

## 3. 官方基准对照（最硬的参照物）

官方 fork 仓库的 `docs/long-context-benchmark-2026-09-14.md` —— 256K 满填充基准：

| 指标 | IQ3（q8_0 主 KV） | IQ4（q5_0 主 KV） |
|---|---:|---:|
| 填充率 | 262,058 / 262,144（99.97%） | 同 |
| **运行期 RSS 峰值** | **13,444 MiB**（13.13 GiB） | **11,250 MiB**（10.99 GiB） |
| 整卡显存峰值 | 15,873 MiB | 15,931 MiB |
| 最低可用显存 | 178.9 MiB | 120.9 MiB |

**对照本机**：

| 项 | 官方基准机 | 本机 |
|---|---:|---:|
| 宿主内存 | 32 GiB（WSL2 可见 19.53 GiB） | **15.5 GiB** |
| 官方 256K 满填充 RSS 峰值 | 11.25–13.44 GiB | — |
| 本机 OOM 击杀线 | — | **≈13.6 GiB** |

> ⚠️ **注意**：官方基准的 13.44 GiB 峰值，在本机**已经越过击杀线**（13.6 GiB）——
> 差之毫厘。**官方配方在本机根本跑不到 256K。**

## 4. 容量推算

### 4.1 宿主侧：128K 能不能撑住

**单次 128K 请求**（干净基线）：

```
246 MiB + 131072 tok × 29.0 KiB/tok
= 246 MiB + 3712 MiB
≈ 3.9 GiB

余量 = 13.6 GiB − 3.9 GiB ≈ 9.7 GiB   ✅ 安全
```

**但要留个心眼——决定风险的是"累积量"，不是"单次 prompt 长度"**：

| 场景 | 观测斜率 |
|---|---:|
| 干净单次请求 | 29.0 KiB/tok |
| **长期 Codex 会话**（70K prompt 下） | **~90 KiB/tok**（约 3 倍） |

按保守斜率重算：

```
128K × 90 KiB/tok ≈ 11.3 GiB
余量 = 13.6 − 11.3 ≈ 2.3 GiB   ⚠️ 仍在线下，但余量收窄
```

**结论：128K 可行，但不是"随便用"，长会话要盯着。**

### 4.2 GPU 侧：有效窗口的上限

| 项 | 值 |
|---|---:|
| 模型权重 | 11,560 MiB（固定） |
| 当前占用 | 14,254 MiB |
| → "其它"（计算缓冲 + MTP + SSM） | ≈ 1,814 MiB |
| **剩余可给 KV** | **≈ 3,010 MiB** |

按 q5_0 的 22 KiB/token → **上限约 140K tokens**。

具体窗口配置下的占用：

| 窗口配置 | budget + reserve | 需要显存 | 余量 | 评价 |
|---|---:|---:|---:|---|
| 官方 IQ3 配方 | 36864 + 16384 = 53248 | 1,144 MiB | ~1.9 GiB | 很宽松 |
| **96K 窗口** | 98304 + 16384 = 114688 | 2,464 MiB | ~546 MiB | **较稳** |
| **真 128K 窗口** | 114688 + 16384 = 131072 | 2,816 MiB | **~194 MiB** | ⚠️ **极紧** |

> **注意区分两个"128K"**：
> - `-c 131072` = 逻辑工作区（客户端能发 12.8 万）→ 成本低
> - **真 128K 有效窗口**（budget 114688）→ 显存只剩 194 MiB 余量，**风险很高**
>
> 本机当前 `--kvmem-budget 24576`，**有效窗口只有 2.4 万**，显存很宽松。
> 要扩大有效窗口，**从 96K 档起步更稳妥**。

## 5. 配置推荐

基于以上数据，给出三档配置：

### 档位 A：稳（当前配置）

```bash
-c 131072 -n 16384 --kvmem-budget 24576 --kvmem-gen-reserve 16384 --kv-dtype q5_0
```

| 项 | 值 |
|---|---|
| 逻辑工作区 | 128K |
| **有效注意力窗口** | **24,576** |
| 宿主占用（单次 128K） | ≈3.9 GiB |
| 显存余量 | 宽松 |
| 适用 | 日常使用、长会话、内存紧张 |

### 档位 B：均衡

```bash
-c 131072 -n 16384 --kvmem-budget 98304 --kvmem-gen-reserve 16384 --kv-dtype q5_0
```

| 项 | 值 |
|---|---|
| 有效注意力窗口 | 98,304 |
| 显存需求 | 2,464 MiB（余 ~546 MiB） |
| 代价 | prefill 变慢（budget 越大越慢） |
| 适用 | 需要真正长上下文理解 |

### 档位 C：对齐官方

```bash
-c 131072 -n 16384 --kvmem-budget 36864 --kvmem-gen-reserve 16384 --kv-dtype q5_0
```

| 项 | 值 |
|---|---|
| 有效注意力窗口 | 36,864（官方 IQ3 配方值） |
| 显存需求 | 1,144 MiB（余 ~1.9 GiB） |
| 适用 | 保守起步，逐步往上试 |

> **调 budget 前先确认**：`total_slots=1` → 压测会**独占服务**，
> 跑之前先看 `/slots` 的 `is_processing` 是否为 `false`。

## 6. 复现方式

```bash
# 被动采样（不打扰服务）：轮数 24，间隔 15s
bash scripts/kvmem-mem-sample.sh "" 24 15

# 单次长 prefill 压测：30 万字符 prompt，anon 上限 10500 MiB 自动中止
bash scripts/kvmem-cap-probe.sh "" 300000 10500

# GGUF 几何与每 token 成本推算
python3 scripts/gguf_kv_math.py /llama/models/Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf
```

**采样输出示例**：

```
TS            anon_MiB  file_MiB shmem_MiB avail_MiB swap_MiB gpu_MiB n_prompt n_decoded
20:13:05          6482     10228         0      9120     2130   13866   131072      1024
```

| 列 | 含义 |
|---|---|
| `anon_MiB` | **KV 池所在，真正要盯的** |
| `file_MiB` | page cache（权重 mmap），**下降是正常的** |
| `avail_MiB` | 宿主可用内存 |
| `swap_MiB` | swap 已用（持续增长 = 危险信号） |
| `gpu_MiB` | 整卡显存占用 |
| `n_prompt` / `n_decoded` | 当前上下文长度 / 已生成数 |
