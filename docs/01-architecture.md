# 01 · KVMem 架构与参数语义

> 这一篇是后面所有排查的基础。**KVMem 的参数名极具误导性**——`-c` 不控制内存、
> `--kvmem-budget` 不是显存预算。搞反一次，整个排查方向就跑偏了。
> 以下每条都标注了**信息来源**（源码注释 / 仓库 README / 实测验证）。
>
> 📖 本篇讲「为什么」，**完整参数清单与推荐值见 [07-parameters.md](07-parameters.md)**。

---

## 1. KVMem 在做什么

传统长上下文推理的痛点是：KV 缓存随上下文线性膨胀，16 GB 显存的 V100 上，
128K 上下文的全精度 KV 就要几十 GiB，根本放不下。

KVMem 的思路是**块稀疏 KV 注意力 + 分层存储**：

```
                     一轮解码时的 KV 访问
                              │
        ┌─────────────────────┴─────────────────────┐
        │                                           │
   命中窗口的块                              未命中的块
   （留在 GPU 显存）                     （下沉到宿主 RAM，再下一层 NVMe）
        │                                           │
   直接参与注意力计算                    按检索分数决定是否回捞
```

具体机制：

1. **切块**：上下文按 **128 token 为一个块**切分。
2. **选择**：每轮解码时，按**注意力/检索分数**从全部历史块中挑一部分，放进 GPU 上的注意力窗口。
3. **重映射**：被选中的块不是原样拼回，而是用 **re-RoPE** 重新映射位置编码——
   否则稀疏拼接后的位置关系会错乱。
4. **分层**：未选中的块落在 **CPU RAM**；再冷一层还有 **NVMe**。

> 来源：`kvmem/include/kvmem/kvmem_store.hpp` 开头的架构注释。

### 关键限制：只作用于标准注意力层

这个模型（`qwen35` 架构）是 **hybrid 架构**：

| 层类型 | 数量 | KVMem 是否介入 |
|---|---:|---|
| 标准全注意力层（full attention） | **16** | ✅ 参与块稀疏调度 |
| DeltaNet 循环层（recurrent） | **48** | ❌ **O(1) 状态，与上下文长度无关** |
| 合计 | 64（+1 MTP） | — |

所以「KV 内存随上下文增长」这件事**只发生在 16 层上**，不是 64 层。
`full_attention_interval = 4` → 每 4 层一个全注意力层。

## 2. 参数语义（逐条澄清）

启动命令长这样：

```bash
llama-kvmem-server -m /models/model.gguf \
  --host 0.0.0.0 --port 8080 \
  -c 131072 -n 16384 \
  --kvmem-budget 24576 --kvmem-gen-reserve 16384 \
  --kv-dtype q5_0 \
  --spec-type draft-mtp --spec-draft-n-max 2 --kvmem-mtp-state replay \
  --api-key "$API_KEY"
```

### `-c` = 逻辑工作区，**不是内存预算**

| 项 | 说明 |
|---|---|
| 字面含义 | 上下文长度上限 |
| **真实含义** | **逻辑工作区**——客户端**允许发送**的历史长度上限 |
| 常见误解 | ❌「`-c` 越大，宿主预分配越多」 |
| **实测** | **`-c 131072` 空载容器 anon 仅 245 MiB** |

> 官方文档里有一条旁证曾被误读：`ista_256k_idle.txt` 记录 `-c 262144` 空载 `rss_kb=11524340`（约 11 GiB）。
> 后来实测推翻了「这是 `-c` 的预分配」——那条记录应是**「模型 + 已填充的池」**，
> 不是空载预分配。**别再用 `-c` 去治 OOM。**

### `--kvmem-budget` = 有效注意力窗口（**不是显存预算**）

这是**最容易搞反**的一个参数。

| 项 | 说明 |
|---|---|
| 字面联想 | ❌「显存预算，单位 MiB」 |
| **真实含义** | **检索可以留在 GPU 上的历史 token 数** = **有效注意力窗口** |
| 源码注释 | `select_budget = 131072 // --kvmem-budget (semantic window tokens)` |
| 仓库 README | *"How many historical tokens retrieval may keep on GPU"* |
| 默认值 | **131072** |
| 特殊值 | `0` = 等于 `n_ctx`（不做限制） |

**后果**：本机设为 `24576` 时，意味着**检索只会把 2.4 万历史 token 放进注意力窗口**。
`-c 131072` 只是「客户端可以发 12.8 万长度的历史」，**模型实际"看得到"的仍然只有 2.4 万**。

> 官方 IQ3 配方用的是 `--kvmem-budget 36864`；用户脚本默认 24576，比官方小 1/3。

**代价曲线**：budget 越大 → 每步检索要搬运更多块 → **prefill 变慢**。
官方基准里「首遍 436.7 t/s → 有效 243.2 t/s」的落差就是这个税。

### `--kvmem-gen-reserve` = decode slack（留给新生成 token 的槽位）

单轮生成**不能超过**这个值。

| 项 | 值 |
|---|---|
| 默认 | **256** |
| 本机现役 | **16384**（默认值的 **64 倍**） |

> ⚠️ **常见误解**：以为默认是 16384。**默认只有 256** ——
> 16384 是本机特意调大的，代价是占掉 GPU KV 池的一大块。
> 官方 `--help` 的原文是 `decode slack (default 256)`。

> 仓库 README：*"GPU KV size is `budget + gen_reserve`"* —— 这是**显存**侧的账，
> 和宿主侧 KV 池是两回事。

### `--kv-dtype` = KV 缓存精度（**真正的内存杠杆**）

可选：`f16 | f32 | q8_0 | q5_0 | q4_0`（**默认 `q8_0`**）。

- 官方 IQ3 配方用 `q8_0`，IQ4 配方用 `q5_0`。
- 混合档 `-ctk q8_0 -ctv q4_0` 是唯一被验证过的混合组合（见下节 V100 硬坑）。
- **MTP draft 的 KV 由 `--spec-kv-dtype` 单独控制，默认 f16**——容易被忽略的一块。

### 投机解码相关

| 参数 | 说明 |
|---|---|
| `--spec-type draft-mtp` | 启用 MTP 投机解码（默认 `none`） |
| `--spec-draft-n-max 2` | draft 最大 token 数（默认 **3**，本机设 2） |
| `--kvmem-mtp-state replay` | MTP 状态的 KVMem 处理方式（默认 `replay`） |

> ⚠ **在 V100 上 MTP 是负收益**（缺 INT8 张量核，见 06 篇），本机实测已确认关闭更好。
> 这里保留 MTP 参数是服务端的既有配置，不代表它在这个硬件上有收益。

## 3. 每 token 的宿主成本（核心公式）

这是整次调优的**定量基础**。

### 模型几何

从 GGUF 元数据读出（`scripts/gguf_kv_math.py` 可复现）：

| 项 | 值 |
|---|---|
| 架构 | `qwen35` |
| 层数 `block_count` | 65（64 + 1 MTP） |
| 全注意力层 | 16（`full_attention_interval = 4`） |
| `head_count_kv` | 4（GQA） |
| `key_length` = `value_length` | 256 |

### 推导

```
每层每 token 元素数 = head_count_kv × (key_length + value_length)
                    = 4 × (256 + 256) = 2048

每 token 总元素数   = 2048 × 16 层全注意力 = 32768 元素
```

### 各精度下的每 token 成本

| dtype | 每元素字节 | 每 token | 说明 |
|---|---:|---:|---|
| f16 | 2 B | **64 KiB** | 基准 |
| q8_0 | 1.0625 B | **34 KiB** | 官方 IQ3 配方 |
| **q5_0** | **0.6875 B** | **22 KiB** | **本机现役** |
| q4_0 | 0.5625 B | **18 KiB** | — |

### 实测验证

| 来源 | 数值 |
|---|---|
| 理论（q5_0） | 22 KiB/token |
| **实测** | **27.1 ~ 29.0 KiB/token** |

两次独立压测（66,686 token 的 prompt，容器 anon 增量 ÷ token 数）得到 27.1 与 29.0 KiB/token，
与 q5_0 理论值同档（偏高的部分来自计算缓冲、页表等额外开销）。

> **这个公式可以直接回答「我这个上下文要多少内存」**：
> `宿主 anon ≈ 基线 + 实际 token 数 × 每 token 成本`

## 4. OOM 击杀线

| 项 | 值 |
|---|---|
| 宿主总内存 | **15.5 GiB** |
| **容器 anon 击杀线** | **≈ 13.6 GiB** |
| 依据 | 9 次 dmesg 记录的 `anon-rss:13622840–13740112 kB` 一致 |

**注意区分两类内存**：

| 类型 | 行为 |
|---|---|
| **anon**（匿名页，KV 池所在） | 顶到击杀线 → OOM SIGKILL |
| **file**（page cache，模型权重 mmap） | **内核优先回收**，下降是正常现象，不是故障 |

> 排查时盯着 `file` 下降会误判；**真正顶墙的是 anon**。

## 5. 官方基准机 vs 本机

| 项 | 官方基准 | 本机 | 差距 |
|---|---:|---:|---|
| 宿主内存 | 32 GiB（WSL2 可见 19.53 GiB） | **15.5 GiB** | **不足一半** |

> **这才是根因**：官方配方是按 32 GiB 宿主内存调的，直接搬到 15.5 GiB 的机器上必然爆。
> 配方必须按比例缩放。

官方 256K 满填充基准（`docs/long-context-benchmark-2026-09-14.md`，fork 仓库内）：

| 指标 | IQ3（q8_0 主 KV） | IQ4（q5_0 主 KV） |
|---|---:|---:|
| 填充率 | 262,058 / 262,144（99.97%） | 同 |
| **运行期 RSS 峰值** | **13,444 MiB**（13.13 GiB） | **11,250 MiB**（10.99 GiB） |
| 整卡显存峰值 | 15,873 MiB | 15,931 MiB |
| 最低可用显存 | 178.9 MiB | 120.9 MiB |

## 6. 一句话小结

```
-c              → 逻辑工作区（客户端能发多长）     默认 2048；便宜，别拿来治 OOM
--kvmem-budget  → 有效注意力窗口（模型能看到多少） 默认 131072；调大 = 变慢，不是变快
--kvmem-gen-reserve → decode slack                 默认 256（本机设 16384）
--kv-dtype      → 每 token 宿主成本（真正的杠杆）  默认 q8_0；34K → q5_0 22K
```

**宿主内存 ≈ 基线 + 实际 token 数 × kv-dtype 每 token 成本**
**击杀线 = 容器 anon ≈ 13.6 GiB（本机 15.5 GiB 宿主）**
